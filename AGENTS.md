# Codex project guidance

## Source of truth and scope

- Read `CLAUDE.md` completely before working. It is the main source of truth for project rules; this file supplements it and must not contradict it. Read `README.md` and the relevant documentation and code before making changes. If guidance conflicts or is unclear, explain the conflict and ask the user before proceeding with affected work.
- This is an unofficial, free, volunteer EU-HEM student website and a learning project. Assume the user is a beginner in programming. Explain important technical concepts, decisions and tradeoffs in clear, beginner-friendly language, defining unfamiliar terms when needed.
- Communicate with the user in English, including progress updates, explanations and final summaries.
- Keep code, technical terms, commands, filenames, comments and the interface in English. Prefer simple, readable solutions and small, focused changes.
- The current phase is **Phase 1: a public information site with no login**, built with plain HTML, CSS and JavaScript and hosted on GitHub Pages.
- `docs/vision.md` describes future ambitions, not permission to implement them. Existing features do not authorize moving beyond Phase 1. Make data structures compatible with future cohorts when useful, without building future systems.
- Discuss frameworks, databases, authentication systems, paid services and major architectural changes with the user before introducing them. Obtain approval before moving beyond the current phase or making Phase 2 technology decisions.

## Architecture and conventions

- Root HTML pages use shared CSS and JavaScript, with no framework or application build step. Node.js scripts support local previews, data generation and validation; dependencies in `package.json` are development tools.
- Course data and study plan rules belong in `content/programme.json`. Reuse existing readers and helpers rather than duplicating course facts or logic.
- Track data belongs in `content/tracks.json`. Study resources live in `content/modules/` as JSON and Markdown; follow `docs/content-format.md` and `docs/tracks-format.md` for relevant edits.
- Thesis data is generated in `content/thesis-archive.json`; use `content/thesis-overrides.json` for corrections and hidden records, and `content/thesis-config.json` for configuration. Follow `docs/thesis-import.md`; do not commit source spreadsheets.
- Reuse `site-nav.js` for shared navigation, `ui.js` and other existing helpers for common behavior, `style.css` design tokens for styling, `icons.svg` for icons and the locally hosted fonts in `fonts/`.
- Preserve mobile usability, light and dark themes, keyboard access and accessible labels. Personal study choices and progress are stored on the device in `localStorage`; do not add remote collection or tracking without discussing it.
- The existing PWA uses `manifest.webmanifest`, `sw.js` and `pwa.js`. Add new pages and scripts to `SITE_FILES` in `sw.js` when appropriate.
- Calendars in `calendar/` are generated by `scripts/build-calendar.js` and refreshed by GitHub Actions. Inspect the generator before editing generated output.

## Privacy, content rights and security

- Never expose private student information in public pages, data files, logs, screenshots, test fixtures or Git history. Use fictional data for development and testing.
- Never commit real student data, secrets or credentials. Keep private data outside the repository; `private-data/` and `*.private.csv` are ignored, but ignore rules alone are not a privacy guarantee. Inspect intended changes before staging.
- Do not publish students' phone numbers or private emails. Any permitted public directory information requires student consent and the documented privacy review. Photos of people require consent.
- A Google Sheet published to the web makes its whole published tab public. Never publish raw form responses; only a separate, minimal directory tab containing consenting students may be considered under the documented process.
- Official lectures, slides and recordings stay on Virtuale: link to them instead of re-uploading. AI summaries may use student-created content only.
- The directory currently uses fictional demo data. Its optional Google Apps Script submission backend is an existing integration, not permission to add accounts or activate real data collection. Read `docs/student-directory.md` and the integration README before related work.
- `join.js` is a reviewed package: do not change it without a new review. Do not enable the submission endpoint or publish real directory data without explicit user approval and the documented go-live checks.
- Keep backend IDs and secrets out of public files. Follow the documented consent-version synchronization between `directory-config.js` and `integrations/directory-apps-script/Code.gs` when privacy meaning changes.
- `privacy.html` is a draft and `contact.html` has a placeholder; do not present them as an approved privacy setup.

## Workflow and collaboration with Claude Code

- Check `git status` before significant work and again before completion. Inspect existing changes and preserve work that belongs to the user or Claude Code; do not overwrite, revert or stage unrelated changes.
- Before a large task, tell the user which files you expect to modify so they can avoid assigning those files to Claude Code. Include expected generated files and version-stamping effects. Update the user if the file scope changes.
- Do not modify files actively being worked on by Claude Code unless the user explicitly assigns them to Codex. If ownership is uncertain and would affect an edit, clarify before editing that file; a clean Git status does not establish ownership.
- Keep changes focused on the requested task. Explain what changed, why it changed, how it was validated and any remaining limitations.
- Tell the user when you notice bugs, security risks, duplicated logic, accessibility problems or better alternatives. Explain their practical impact; discuss substantial follow-up work before expanding scope.
- Use sensible, focused Git commits at good checkpoints when committing is authorized. While the user is still learning, ask before committing important work unless they have already explicitly approved that commit. Explain what the proposed commit contains. Review the diff and staged files first, and use clear English commit messages. An explicit request not to commit takes precedence; do not commit the initial creation or this requested update of this file.

## Validation

- Choose checks appropriate to the change; explain what each relevant check establishes. Do not claim tests passed unless they were run successfully, and report checks that could not run.
- Preview locally with `node scripts/preview.js` at `http://localhost:8000` when visual or browser behavior needs checking.
- Run `node scripts/check-content.js` for content and related integrity checks. For course-data changes, `node scripts/check-programme.js` compares with the live official UniBo timetable and needs network access.
- For style changes, check relevant pages on mobile and desktop and in both themes; use `node scripts/check-contrast.js` for WCAG AA color contrast.
- For directory changes, follow `docs/student-directory.md` and run `npm test` when appropriate. `npm install` supplies the development test tools; browser tests use installed Chrome. These tests use dummy services and do not replace testing a deployed integration.
- After changes to any `.html`, `.css` or `.js` file, run `node scripts/stamp-versions.js` as required by `README.md`. It updates page asset fingerprints and the service-worker version, potentially touching multiple files. Account for Claude Code's active files before running it, then validate the resulting changes.
- A documentation-only change to this file does not require version stamping or application tests. Review its consistency with the source documentation and confirm that only the requested file changed.
